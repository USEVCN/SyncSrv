# Security and backup boundaries

The center and its administrators are trusted to configure device backup operations. A device Agent executes with the service identity chosen by its local administrator. LocalSystem/root can read substantial local data: bind only to a center you administer and protect its administrator accounts. A compromised center administrator is outside the Agent's untrusted-user boundary. The center cannot currently be treated as an untrusted multi-tenant controller.

Use loopback HTTP during local development. Use verified HTTPS for remote administration and device control. Explicit private-IP HTTP exceptions exist for LAN testing; they are not suitable for an untrusted network. SFTP host fingerprints must be verified independently. FTP and HTTP WebDAV do not provide confidential transport. SMB signing authenticates messages but does not itself guarantee content encryption; require a confidential network or encrypted transport/storage configuration.

Local center file operations use the bundled standard-library-only native bridge and `os.Root`. The bridge has no listener, shell, enrollment, password or network function. Requests travel over private child-process pipes. All operations after root selection are relative to a held root directory handle, including reads, writes, directory creation, rename, removal and modification time. Malformed frames terminate the channel. The bridge is mandatory; there is no fallback to check-then-open Java paths when it is absent.

Protect configured root directories and their ancestors from untrusted replacement before the root is opened. Filesystem mounts, hard links, special device files, administrative access and a compromised host are not a general-purpose sandbox boundary. Do not run backup roots in directories writable by unrelated host users. Symlinks are rejected by policy, and native containment still applies if an attacker races the precheck. Retention and restore destinations must use dedicated directories.

Backup nodes describe completed verified file states. They are not VSS/APFS/database application-consistent snapshots. Rapid intermediate versions can be coalesced while preserving an eventual verified state and execution records. No claim is made that every transient intermediate byte sequence is retained. Watcher overflow, offline periods and missing change-journal history require reconciliation.

File contents are not encrypted at rest by SyncSrv. Use encrypted filesystems or storage encryption when required. Restore does not reconstruct arbitrary ACLs, ownership or extended attributes. Keep metadata and its associated keys with a consistent copy of the backup/archive libraries. Test recovery to a separate empty directory and compare content hashes before relying on a deployment.

Source publication covers reviewed source only. Windows/Linux/macOS cross-compilation does not establish real installer, junction, power-loss, NAS firmware, disk-full or suspend/resume acceptance. Those checks remain requirements for formal platform-specific binary releases. No historical local JAR, archive, private deployment or publisher key is included in this repository.
