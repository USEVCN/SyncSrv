# Windows 目录删除与监听修复 · 0.14.0-dev

## 问题与原因

实机现象：Windows 源目录下的文件夹已授予当前用户完全控制，Agent 服务运行时删除失败，停止服务后可以删除。不能将此现象继续归因于用户权限或 LocalSystem 账户。

代码检查发现两处会阻碍删除/释放的实现：

1. 原 Windows 监听与 Linux 共用 fsnotify 逐子目录注册。收到新建目录通知时，消费通知的同一 goroutine 同步执行 `WalkDir → Add`；Windows `Add` 等待 I/O 线程回复，而 I/O 线程可能正在等待该消费者接收下一条通知，形成相互等待。此时通知处理与已删除目录句柄的释放都可能停滞。仅看到 `FILE_SHARE_DELETE` 不能排除这个生命周期问题。
2. 源文件和源根目录句柄一直保留到 备份库端回读 SHA-256 校验结束。Windows 的待删除文件/目录需等待相关句柄释放；网络校验不应继续占用已读完的 源目录。

尚未取得故障 Windows 进程的线程栈，不能证明本次每一次删除失败都由同一个等待点造成。

## 本版改动

- Windows 使用 `ReadDirectoryChangesW` 的 `bWatchSubtree=TRUE`，每个任务根目录一个递归监听，不再对每个子目录长期开句柄，也不在通知循环中调用 `Add`。新增、移入、重建的子目录自动受覆盖。
- 为检测根目录本身被删除/改名，另设一个父目录的非递归监听，仅处理目标根目录名称；不会扫描父目录下的其他树。监听资源按任务根目录数增长，而非子目录数增长。
- 所有监听句柄允许共享读、写、删除。停止时先取消全部异步读取，等待完成后由各自工作器关闭句柄；停止操作可重复调用。
- 启动返回前已提交首次异步监听；随后沿用重启基线校准和本机持久队列。重命名的旧、新路径都进入变化队列。
- 通知溢出、解码失败、根目录变化会使覆盖状态失效并触发已有补扫/重新监听流程，不会静默忽略。
- 打开源文件后即释放临时根目录句柄。上传结束检查文件元数据并释放源文件，再校验 备份库；校验结束重新确认 源目录的路径、文件身份、大小及修改时间。源目录被删除或替换时不确认旧清单为成功。

仍在实际读取/上传中的文件必须保留读句柄；本版没有引入 VSS 或先复制本地临时副本，不能保证正在传输的文件立即完成物理删除。修复目标是消除监听死锁、长期占用子目录，以及校验 备份库期间的不必要占用。

依据：[Microsoft ReadDirectoryChangesW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-readdirectorychangesw)、[CancelIoEx 的取消完成要求](https://learn.microsoft.com/en-us/windows/win32/api/ioapiset/nf-ioapiset-cancelioex)。

## 更新与验收

本版不修改中心协议，不需要因本修复重启 IDEA 后端。在 Windows 现有安装目录右键 `update.bat` → 以管理员身份运行；升级会保留设备身份、配对和事件队列。若已有脚本过旧，下载完整新版 ZIP 解压到另一个目录，从其中运行 `update.bat`，不要覆盖或删除现有 data 目录，也无需重新安装配对。

确认 `syncsrv-agent.exe version` 显示 `0.14.0-dev windows amd64`（ARM 设备为 arm64），并确认服务 Running。升级前已停止的服务保持停止，需要再运行 `start.bat`。

实机验收时使用新建的专用测试文件夹：

1. 服务保持运行，新建多层目录并写入测试文件，确认中心收到变化。
2. 重命名、删除该测试目录，确认不再因监听句柄长期占用而失败。
3. 在原路径重新创建目录和文件，确认仍可收到后续变化，无需重启 Agent。
4. 确认删除事件完成归档处理；源目录、备份库与归档库的最终状态与执行记录一致。

已增加跨平台通知解码/源文件删除与替换回归，以及 Windows 专用的运行中删除、重命名、目录重建、连续创建删除、根目录变化和空闲取消测试。Windows 专用用例需在真实 Windows 执行；交叉编译成功不等于 Windows 实机通过。
