# 全局并发与平台排查（2026-09-19）

> 历史记录：本文保留当时的 MySQL 环境、测试和故障证据，不作为当前默认部署配置。自 2026-10-21 起默认使用 H2；安装、迁移和备份以 H2迁移与恢复（内部历史证据未随公开源码分发；现行边界见 SECURITY-MODEL.md） 及主 README 为准。

本轮针对“看起来仍是单线程”检查中心 Java、源端 Go、Linux inotify 和 macOS FSEvents。源码修复由两个正在协作的任务共同集成，Agent 版本与中心发布统一进行。本文不把源码通过测试等同于用户 NAS 的吞吐验收。

## 已确认并修复

| 链路 | 原问题 | 修改与保护 |
|---|---|---|
| 中心全量/变化范围内容校验 | 逐个文件读取和计算哈希 | 元数据枚举后，有界并行哈希；每个 worker 独立协议连接，哈希前后核对大小/修改时间/类型，文件变动则整批拒绝提交 |
| B/C → D 合成备份 | 逐文件恢复；部分会话关闭异常被忽略 | 复用任务中心并发上限，每 worker 独立 B/C 与 D 会话；目录先准备，文件校验后发布，全部 worker 关闭并通过最终目录复核后才生成收据 |
| 合成备份 SMB 读取 | 三参数读取上限被 RestoreDestination 包装器丢弃 | 转发子目录前缀、偏移、长度，避免分块回读无界预读 |
| 设备端 B→C 复制/本地校验命令 | 中心反复返回第一条 RUNNING；Agent 单 worker | 中心能力协商 + activeIds 排除已领取命令；新 Agent 最多 4 条无冲突命令并行，旧中心兼容顺序执行；取消等全部写线程退出 |
| 设备繁忙与领取超时 | 忙碌排队超过 15 秒被当成未领取，可能错误回退中转 | 在线且已有命令执行时续延排队；失联结果未知保留对账，禁止凭超时另起并行中转 |
| 设备目录绑定 | 多 worker 反复截断写同一挑战文件 | 同端点发布短锁，已匹配的标记直接复用 |
| 源端多文件进度上报 | 带着共享进度锁发送 HTTP，一个慢请求阻塞其他文件 worker | 锁内更新/生成快照，锁外发送请求；事件确认与断点语义不变 |
| 中心 SFTP 读写 | 单文件按请求等待，写入块为 64 KiB | 使用 SSHJ 已有 8 请求窗口；失败有界排空 ACK，无新依赖。实测库的尾部 length 提示不严格，故有界读取最后 512 KiB 改用精确偏移同步读取，前部及无界整文件读取、写入保留管线 |
| 源端 SFTP 写入 | 带限速包装的 reader 走库的默认顺序写，每块等待应答 | 显式使用原生 4 请求管线；失败先收拢请求再截断不连续尾部，续传前缀 SHA、最终 SHA 与 Sync 保留 |
| 校验阶段嵌套进度 | 结束内层校验时外层字节数归零 | 恢复原路径、阶段、已读字节和总字节 |
| Linux 新目录监听 | inotify 接收线程同步递归遍历新目录，拖住其他根变化 | 动态登记移至 4 个有界 worker，登记完成补发目录范围校准 |
| Linux 移动/删除/重建 | watch 跟随 inode 但路径仍旧；失效 watch 删除 EINVAL；旧删除事件可能移除同名新目录 watch | 按 inode 核对登记与清理，重命名后重建子树路径监听，失效可恢复且触发范围校准 |
| macOS 文件监听 | 丢弃 MustScanSubDirs 标志；停止时可能不再消费原生回调 | 触发完整校准；停止期间继续排空事件，再等待监听退出 |

目录创建/移除按依赖顺序，文件完成记录与审计提交有序；扩大并发不跳过验证。界面新增当前/峰值“并行校验”，与备份文件数分开统计。性能报告保留文件并发、阶段等待、传输/校验字节与失败信息。

## 仍存在的顺序环节与边界

- **源端单个大文件的 SMB I/O**：Go SMB 当前仍逐个 256 KiB 请求等待；多文件同时传不等于单文件流水线。中心 SMB 已有有界预读/写入与同 NAS COPYCHUNK，两者必须分别看待。本轮没有自研 SMB 分块乱序传输。
- **多个备份任务**：中心全局任务队列、源端按任务推送仍顺序，单个任务内可多文件并发。这样保持 B/C 版本更新、合成读取及共享限速隔离；公平队列游标解决了前一任务失败导致后续任务饥饿的问题。取消这层隔离需要任务资源锁和共享预算，不能直接删锁。
- **有限速设备存储命令**：目前顺序执行，避免每个命令各用一次完整限速导致总速率翻倍。报告会明确标注；上限 4 是能力上限，实际运行数可能为 1。该保护只覆盖设备 HASH/COPY 通道；尚无跨多个 Agent、源上传与中心 I/O 的统一全局带宽调度，不能宣称全系统总速率已被一个预算严格限制。
- **审计和 MySQL**：Store 当前使用单连接/全局锁读写，整条审计链校验也持锁；文件 I/O 已移出此锁。审计写必须有序，未来可拆独立只读连接/固定链头快照验证并增加 DB 等待指标，不能直接移除完整性锁。
- **目录元数据**：初次递归建立监听、树枚举、按层创建父目录、按深度删目录、未完成日志恢复仍有顺序依赖。FTP 深目录反复 LIST/stat 还会放大往返；不是 CPU 线程数不足。
- **WebDAV**：最终集成已补齐请求/正文空闲超时和故障取消；持续有进展的慢传不设整文件总期限。11项故障回归和原3项备份恢复测试通过，见 系统审计报告（内部历史证据未随公开源码分发；现行边界见 SECURITY-MODEL.md）。
- **存储持久化**：本地分块 fsync、校验、断点提交不能当作多余开销删除。并发对机械盘可能变慢，建议从 4 起按实际报告调整。
- **外部篡改窗口**：D 最终再次枚举并核对目录集合、类型、大小和修改时间；这仍不是原子文件系统快照。运行期间应由 SyncSrv 独占备份目录写入。

## 验证口径

真实并发测试使用同步屏障让 4 条实际读取/复制同时处于进行中，断言所有请求完成前无恢复节点/收据；包含一个 worker 失败、其他请求收拢、B/C 不变、同 D 重试恢复。不是仅检查线程池参数。

平台验收区分：macOS 原生 FSEvents + race；Linux ARM64 在现有 Docker Linux 内核中执行真实 inotify；Windows、Linux x64、群晖 DSM 的服务安装、权限与长时间 NAS 负载仍需各自实机验收，交叉编译或管理脚本模拟不能替代。

已完成的验证（后续统一发布任务还会执行集成检查）：

- 中心第一轮 ScannerParallelTest、RestoreParallelTest、CenterParallelTest、SyncRecoveryTest、IncrementalSyncTest、DeviceExecutionTest、DeviceExecutionConcurrencyTest 通过；后补恢复失败与有界读取、中心SFTP管线的10项定向也全部通过。
- 前端 26 个测试文件、88 项测试通过，生产构建通过。
- macOS Agent 全量 race 通过（16.680 秒，含源端 SFTP 新管线）；原生监听重复 5 轮通过。
- Linux 原生监听 25 轮通过；Linux ARM64 全量普通用户测试与服务管理模拟结果见 [平台报告](Linux-macOS监听并发排查-20260919.md)。包含 SFTP 新增后的最后76组全量测试，0跳过、0失败。
- 本轮没有测量真实 NAS 的端到端 MB/s，也没有更改系统服务或真实备份文件。

中心 SFTP 的补充验证：macOS Java17 对临时真实 SSHD 发起请求，首个读/写响应阻塞时另有7个请求等待，证明8请求窗口；读取上限不越界、3个错误ACK排空、短源后按偏移恢复、完整哈希、原4MiB/s共享limiter均通过。末512KiB精确尾读会保留部分顺序开销，小文件依赖文件级并发；本报告不将此本地协议验证替代Linux/NAS网络吞吐验收。
